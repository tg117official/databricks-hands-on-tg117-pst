Normalization Through Problems and Solutions

Start with difficult-to-use sales data, experience the problems, and improve the design step by step through 1NF, 2NF, 3NF and BCNF.

1. The normalization journey

Normalization separates different business subjects into suitable tables. Each stage fixes a specific kind of dependency problem.

1NFOne value in each field and no repeating product groups.
2NFEvery non-key field depends on the complete key.
3NFNon-key fields do not determine other non-key fields.
BCNFEvery determinant is a candidate key.
Simple working method: inspect the problem, understand the dependency, redesign the tables, load the data, and verify that the business result remains correct.

3. First Normal Form: one value in each field

First inspect what happens when 1NF is not maintained.

Several values in one field501,502 is a list, not one product ID.
Lists can lose alignmentA missing quantity can connect later quantities to the wrong products.
Searching becomes awkwardA product search requires string functions instead of a normal equality check.
Totals become difficultSUM() cannot directly add values stored inside comma-separated text.
Normal joins are blockedA list of product IDs cannot use a simple foreign-key relationship.
Indexing is weakAn index cannot efficiently find each value hidden inside a list.
Constraints are missingA foreign key cannot validate every product ID inside the same field.
Reports need parsingEvery report must first split and match the product, quantity and price lists.
Run 1A — Experience the awkward product search
MySQL
USE ecomsphere_normalization;

SELECT
    order_id,
    product_ids,
    product_names
FROM sales_unnormalized
WHERE FIND_IN_SET('501', product_ids) > 0
ORDER BY order_id;
1NF: each field contains one value, repeating groups are removed, and every row can be uniquely identified.

1NF ER diagram

Each row now represents one product within one order. The pair (order_id, product_id) identifies the row.

Practice assumption: the same product appears at most once in an order. A production system that permits repeated product lines would normally use an order_item_id or a line number.

4. Second Normal Form: depend on the complete key

The primary key of sales_1nf is the composite key (order_id, product_id). A composite key contains more than one column.

Functional dependency: one value determines another value. For example, one product_id determines one product_name. The value on the left is called the determinant.
order_id → order_date, customer_id
product_id → product_name, category_id
(order_id, product_id) → quantity, unit_price

Partial dependency means that a non-key field depends on only part of a composite key. Here, order_date depends only on order_id, while product_name depends only on product_id.

Challenges before 2NF

Order details repeatThe date and customer are copied for every product in the same order.
Product details repeatThe same product name appears in every order containing that product.
Update anomalyUpdating only one copy can give the same product two different names.
Insertion anomalyA product cannot be stored until an order also exists.
Deletion anomalyDeleting the last sale of a product can remove its only description.
Unnecessary storageLong descriptions are repeated in many transactional rows.
Large updatesOne product-name correction may touch thousands of sales rows.
Quality riskRepeated text can develop different spellings, casing or spacing.

2NF: the table is already in 1NF, and every non-key field depends on the complete primary key. Partial dependencies are removed.

2NF ER diagram

Order-only fields move to orders_2nf. Product-only fields move to products_2nf. Quantity and transaction price remain in order_item_2nf because they describe one order-product combination.

Run 2B — Create the 2NF tables
MySQL
USE ecomsphere_normalization;

CREATE TABLE orders_2nf
(
    order_id          INT PRIMARY KEY,
    order_date        DATE NOT NULL,
    customer_id       INT NOT NULL,
    customer_name     VARCHAR(100) NOT NULL,
    customer_city     VARCHAR(80) NOT NULL,
    customer_country  VARCHAR(80) NOT NULL
) ENGINE = InnoDB;

CREATE TABLE products_2nf
(
    product_id             INT PRIMARY KEY,
    product_name           VARCHAR(150) NOT NULL,
    category_id            INT NOT NULL,
    category_name          VARCHAR(100) NOT NULL,
    category_manager_id    INT NOT NULL,
    category_manager_name  VARCHAR(100) NOT NULL
) ENGINE = InnoDB;

CREATE TABLE order_item_2nf
(
    order_id     INT NOT NULL,
    product_id   INT NOT NULL,
    quantity     INT NOT NULL,
    unit_price   DECIMAL(10,2) NOT NULL,

        FOREIGN KEY (product_id)
        REFERENCES products_2nf(product_id)
) ENGINE = InnoDB;

MySQL
SELECT

    p.product_name,

5. Third Normal Form: remove indirect dependencies

Transitive dependency: a key determines one non-key field, and that non-key field determines another non-key field.
order_id → customer_id → customer_name, customer_city, customer_country
product_id → category_id → category_name, category_manager_id
category_manager_id → category_manager_name

Challenges before 3NF

Customer details repeatThe same customer information appears in every order.
Customer update anomalyA city change must be repeated across all of the customer’s orders.
Customer insertion anomalyA customer cannot be stored until an order exists.
Customer deletion anomalyDeleting the last order can remove the customer’s only description.
Category details repeatEach product repeats the category name and manager.
Category update anomalyRenaming a category requires an update to every product in it.
Conflicting ownershipProducts in one category could accidentally show different managers.
Mixed responsibilitiesOrders maintain customer data, while products also maintain category and manager data.

MySQL

    category_manager_name

3NF: the table is already in 2NF, and non-key fields do not depend on other non-key fields. Transitive dependencies are removed.

3NF ER diagram

Customer, category and category-manager information now have their own tables. Transaction tables keep keys that point to those business subjects.

SELECT

    p.product_name,
    cat.category_name,
    SUM(oi.quantity) AS quantity_sold,
    SUM(oi.quantity * oi.unit_price) AS sales_amount
FROM order_item_3nf AS oi

3NF result: customer, order, product, category and manager data can now be maintained independently. Operational updates are safer, although analytical reports require more joins.

6. BCNF: every determinant must be a candidate key

Most practical operational designs stop at 3NF. BCNF handles a smaller set of dependency problems that may remain when a table has more than one candidate key.

Candidate key: a minimal field or field combination that can uniquely identify a row.

Consider a course-allocation table with these rules:

  • A student can attend many courses.
  • Each instructor teaches exactly one course.
  • A course can have multiple instructors.
  • A student has one instructor for a selected course.
(student_id, course_id) → instructor_id
(student_id, instructor_id) → course_id
instructor_id → course_id

The first two combinations are candidate keys. Every field participates in a candidate key, so this example can satisfy 3NF. It still violates BCNF because instructor_id determines course_id but is not a candidate key for the complete table.

Challenges before BCNF

Course assignment repeatsAn instructor’s course is copied for every student.
Update anomalyUpdating only one row can show the same instructor teaching different courses.
Insertion anomalyAn instructor cannot receive a course until a student exists.
Deletion anomalyDeleting the last student can remove the instructor’s course assignment.
Hidden determinantinstructor_id determines course_id but does not identify a complete row.
Difficult enforcementThe original structure does not directly enforce one course per instructor.
Run 4A — Create the 3NF course allocation and expose the problem
MySQL
USE ecomsphere_normalization;

CREATE TABLE course_assignment_3nf
(
    student_id     INT NOT NULL,
    course_id      VARCHAR(50) NOT NULL,
    instructor_id  INT NOT NULL,

    PRIMARY KEY (student_id, course_id),

    CONSTRAINT uq_student_instructor
        UNIQUE (student_id, instructor_id)
) ENGINE = InnoDB;

INSERT INTO course_assignment_3nf
(
    student_id,
    course_id,
    instructor_id
)
VALUES
    (1, 'SQL', 10),
    (1, 'PYTHON', 20),
    (2, 'SQL', 10),
    (2, 'PYTHON', 20),
    (3, 'SQL', 30);

SELECT *
FROM course_assignment_3nf
ORDER BY student_id, course_id;

START TRANSACTION;

UPDATE course_assignment_3nf
SET course_id = 'DATA_MODELLING'
WHERE student_id = 1
  AND instructor_id = 10;

SELECT
    instructor_id,
    COUNT(DISTINCT course_id) AS number_of_courses
FROM course_assignment_3nf
GROUP BY instructor_id
HAVING COUNT(DISTINCT course_id) > 1;

ROLLBACK;
BCNF: every determinant must be a candidate key. Here, instructor_id determines course_id, so that relationship needs its own table.

BCNF ER diagram

The instructor-course relationship is stored once. Student allocation refers to the instructor.

Run 4B — Create and load the BCNF tables
MySQL
CREATE TABLE instructor_course_bcnf
(
    instructor_id  INT PRIMARY KEY,
    course_id      VARCHAR(50) NOT NULL
) ENGINE = InnoDB;

CREATE TABLE student_instructor_bcnf
(
    student_id     INT NOT NULL,
    instructor_id  INT NOT NULL,

    PRIMARY KEY (student_id, instructor_id),

    CONSTRAINT fk_student_instructor_bcnf
        FOREIGN KEY (instructor_id)
        REFERENCES instructor_course_bcnf(instructor_id)
) ENGINE = InnoDB;

INSERT INTO instructor_course_bcnf
(
    instructor_id,
    course_id
)
SELECT DISTINCT
    instructor_id,
    course_id
FROM course_assignment_3nf;

INSERT INTO student_instructor_bcnf
(
    student_id,
    instructor_id
)
SELECT DISTINCT
    student_id,
    instructor_id
FROM course_assignment_3nf;
Run 4C — Reconstruct and validate the course allocation
MySQL
SELECT
    si.student_id,
    ic.course_id,
    si.instructor_id
FROM student_instructor_bcnf AS si
JOIN instructor_course_bcnf AS ic
    ON si.instructor_id = ic.instructor_id
ORDER BY
    si.student_id,
    ic.course_id;

SELECT
    instructor_id,
    COUNT(*) AS course_rows
FROM instructor_course_bcnf
GROUP BY instructor_id
HAVING COUNT(*) > 1;
BCNF result: the instructor’s course is stored once, can be updated once, and remains available even when no student allocation exists.

Normal formMain challengeDesign response
1NFLists, repeating groups and several values in one fieldCreate one row per business occurrence.
2NFA field depends on only part of a composite keySeparate order, product and order-item data.

Final checkpoint

  • Every field in the 1NF table contains one value.
  • Partial dependencies are removed in 2NF.
  • Transitive dependencies are removed in 3NF.
  • Every determinant is a key in the BCNF tables.
  • Sales totals match before and after normalization.
  • The final 3NF model protects operational data but needs several joins for reporting.
